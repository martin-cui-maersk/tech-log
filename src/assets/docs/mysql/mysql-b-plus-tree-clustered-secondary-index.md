# MySQL 索引为什么用 B+ 树？聚簇索引与非聚簇索引有什么区别？

> 面试高频题，但很多人只背结论。本文从磁盘 IO、扇出、范围查询等角度讲清楚 B+ 树的选型逻辑，再对比聚簇索引与非聚簇索引的存储结构、回表机制和工程实践。

---

## 一、为什么 MySQL（InnoDB）索引用 B+ 树？

### 1.1 先看 B+ 树的结构

B+ 树是一棵**多路平衡查找树**，核心特征：

- **非叶子节点只存索引键 + 子节点指针，不存数据**；
- **所有数据都存放在叶子节点**；
- **叶子节点之间用双向链表连接**，且所有叶子节点在同一层；
- 每个节点对应一个磁盘页（InnoDB 默认 16KB）。

```
                 [ 30 | 60 ]                 ← 非叶子节点：只存键
                /     |      \
        [10|20]    [40|50]    [70|80]        ← 非叶子节点
        /  |  \    /  |  \    /  |  \
      叶子→叶子→叶子→叶子→叶子→叶子→叶子     ← 叶子节点：存数据，双向链表
```

### 1.2 为什么不是其他数据结构？

| 数据结构 | 问题 |
|---|---|
| **二叉搜索树 / 红黑树** | 每个节点只有 2 个叉，树高约 log₂N。千万级数据树高约 20+ 层，每层一次磁盘 IO，查询要 20+ 次 IO，太慢 |
| **B 树** | 非叶子节点也存数据，同样大小的磁盘页能存的键更少，扇出小、树更高；范围查询需要中序遍历，不如 B+ 树叶子链表高效 |
| **哈希表** | 等值查询 O(1)，但**不支持范围查询、排序、最左前缀匹配**，无法满足 `WHERE age > 20 ORDER BY name` 这类需求 |
| **跳表** | 内存结构，磁盘上不适用；且范围查询、磁盘 IO 局部性不如 B+ 树 |
| **LSM 树** | 写性能好，但读放大严重，适合写多读少场景；MySQL 的 InnoDB 是读多写少优化 |

### 1.3 B+ 树的优势

**① 矮胖，磁盘 IO 少**

InnoDB 一个页 16KB，非叶子节点只存「键 + 指针」。假设主键 bigint 8 字节、子页指针约 4 字节，再算上页内记录头等开销，一个非叶子节点大约能存一千多个键（教学上常近似为 16KB / (8 + 6) ≈ 1170）：

```
约 1000+ 个键 / 页
```

三层 B+ 树：

- 第一层 1 个节点，1170 个键；
- 第二层 1170 个节点，约 137 万个键；
- 第三层叶子节点约 16 亿个键。

**千万级数据通常 3 层，查一次最多 3 次磁盘 IO**，而且根节点常驻内存，实际往往 2 次 IO 甚至更少。

**② 范围查询高效**

叶子节点是双向链表，`WHERE id BETWEEN 100 AND 200` 只需定位到 100，然后顺着链表扫描到 200，不需要回到上层节点。

**③ 查询性能稳定**

所有数据都在叶子节点，每次查询都必须走到叶子层，路径长度一致，**查询时间复杂度稳定为 O(log N)**，不会出现 B 树中"有的数据在非叶子节点、查得快，有的在叶子节点、查得慢"的情况。

**④ 全表扫描高效**

全表扫描只需遍历叶子节点链表，不需要遍历整棵树。

**⑤ 排序天然有序**

叶子节点按键有序排列，`ORDER BY` 可以利用索引顺序，避免额外排序。

### 1.4 一句话总结

> B+ 树用**非叶子节点只存键**换来了**更高的扇出、更矮的树、更少的磁盘 IO**；用**叶子节点链表**换来了**高效的范围查询和全表扫描**；用**数据全在叶子层**换来了**稳定的查询性能**。这是磁盘数据库在"读多写少、范围查询多"场景下的最优解。

## 二、聚簇索引与非聚簇索引

> 讨论前提：**InnoDB**。MyISAM 的索引都是非聚簇的，叶子节点存的是数据地址，不是主键。

### 2.1 聚簇索引（Clustered Index）

**定义：** 索引和数据存放在一起，**叶子节点直接存储整行数据**。

InnoDB 的主键索引就是聚簇索引：

```
聚簇索引（主键 id）
        [ 30 | 60 ]
       /     |      \
  [10|20] [40|50] [70|80]
   /  \     /  \     /  \
叶子节点：存完整行数据
[id=10, name=..., age=..., ...]
[id=20, name=..., age=..., ...]
...
```

**特点：**

- 一张表**只有一个**聚簇索引；
- 优先选主键；没有主键，选第一个 `NOT NULL UNIQUE` 索引；都没有，InnoDB 生成隐藏的 6 字节 `row_id`；
- 数据和索引在同一个 B+ 树中，**找到索引就找到了数据**；
- 按主键顺序组织数据，主键顺序影响物理存储顺序。

### 2.2 非聚簇索引（Secondary Index / 辅助索引）

**定义：** 索引和数据分开存储，**叶子节点存储索引列 + 主键值**，不存整行数据。

```
二级索引（name）
        [ Alice | Bob | Carol ]
       /          |           \
叶子节点：存 name + 主键 id
[Alice, id=10] → [Bob, id=20] → [Carol, id=30]
```

**特点：**

- 一张表**可以有多个**非聚簇索引；
- 叶子节点只存「索引列 + 主键值」；
- 查询非索引列时，需要**回表**：先查二级索引拿到主键，再拿主键去聚簇索引查整行。

### 2.3 回表（Bookmark Lookup）

```sql
-- 假设 name 上有二级索引
SELECT * FROM user WHERE name = 'Alice';
```

执行过程：

1. 在 `name` 二级索引中找到 `Alice`，拿到主键 `id = 10`；
2. 拿 `id = 10` 去聚簇索引查整行数据；
3. 返回结果。

**第 2 步就是回表**。如果查询的列都在二级索引中，就不需要回表，这就是**覆盖索引**。

### 2.4 覆盖索引（Covering Index）

```sql
-- name 上有二级索引 (name, id)
SELECT id, name FROM user WHERE name = 'Alice';
```

查询的列 `id`、`name` 都在二级索引叶子节点中，**不需要回表**，直接返回。

```sql
-- 联合索引 (name, age)
SELECT name, age FROM user WHERE name = 'Alice';
```

同样可以覆盖，不需要回表。

**覆盖索引是优化查询的重要手段**：`EXPLAIN` 的 `Extra` 出现 `Using index` 就表示用了覆盖索引。

### 2.5 两者对比

| 对比项 | 聚簇索引 | 非聚簇索引（二级索引） |
|---|---|---|
| **叶子节点内容** | 整行数据 | 索引列 + 主键值 |
| **数量** | 一张表 1 个 | 一张表多个 |
| **数据与索引** | 在一起 | 分离 |
| **查询非索引列** | 直接返回 | 需要回表 |
| **查询索引列** | 直接返回 | 直接返回（覆盖索引） |
| **主键长度影响** | 影响整行存储 | **所有二级索引叶子节点都存主键，主键越长，二级索引越大** |
| **插入顺序影响** | 主键顺序影响页分裂 | 无直接关系 |
| **典型场景** | 主键查询 | 普通字段查询、联合索引 |

## 三、由聚簇索引引出的工程实践

### 3.1 为什么推荐自增主键？

**自增主键**：每次插入都在 B+ 树最右侧追加，顺序写入，**很少页分裂**，性能好。

**随机主键（如 UUID）**：插入位置随机，可能导致中间页分裂、页碎片，写入性能差，且二级索引体积更大。

```sql
-- 推荐
id BIGINT UNSIGNED AUTO_INCREMENT PRIMARY KEY

-- 不推荐（除非有明确分库分表需求）
id VARCHAR(36) PRIMARY KEY  -- UUID
```

### 3.2 为什么主键不宜过长？

二级索引叶子节点存的是**主键值**。主键越长：

- 每个二级索引叶子节点能存的条目越少；
- 二级索引体积越大；
- 回表成本越高。

所以主键优先用 `BIGINT`，而不是长字符串。

### 3.3 为什么推荐覆盖索引？

- 避免回表，减少一次聚簇索引查找；
- 减少磁盘 IO；
- 二级索引通常比聚簇索引小，扫描更快。

```sql
-- 联合索引 (user_id, status, created_at)
-- 以下查询可以覆盖，不需要回表
SELECT user_id, status, created_at
FROM orders
WHERE user_id = 100 AND status = 1
ORDER BY created_at DESC;
```

### 3.4 联合索引与最左前缀原则（重点澄清）

#### 3.4.1 最左前缀原则约束的是什么？

**最左前缀原则约束的是「索引列的顺序」和「查询条件是否包含最左列」，不是 SQL 里 WHERE 条件的书写顺序。**

MySQL 优化器在生成执行计划时，会**自动重排 WHERE 条件**去匹配索引列顺序。所以：

```sql
-- 索引 idx_abc (a, b, c)
WHERE a = 1 AND b = 2 AND c = 3
WHERE c = 3 AND b = 2 AND a = 1
WHERE b = 2 AND a = 1 AND c = 3
```

这三种写法**完全等价**，都能用上 `idx_abc (a, b, c)` 的全部三列。你说的 `bac`、`cba` 作为 WHERE 条件顺序，确实可以。

**真正不能用的，是查询条件里缺少最左列 `a`**：

```sql
-- 索引 idx_abc (a, b, c)
WHERE b = 2 AND c = 3;  -- 缺少最左列 a，常规情况下用不上 idx_abc
```

#### 3.4.2 完整对照表（索引 `idx_abc (a, b, c)`）

| WHERE 条件 | 能否用 `idx_abc` | 用到哪些列 | 说明 |
|---|---|---|---|
| `a = 1` | ✅ | a | 最左前缀 |
| `a = 1 AND b = 2` | ✅ | a, b | 最左前缀 |
| `a = 1 AND b = 2 AND c = 3` | ✅ | a, b, c | 完整最左前缀 |
| `b = 2 AND a = 1` | ✅ | a, b | WHERE 顺序不影响，优化器重排 |
| `c = 3 AND b = 2 AND a = 1` | ✅ | a, b, c | WHERE 顺序不影响，优化器重排 |
| `a = 1 AND c = 3` | ⚠️ 部分 | 只有 a | 缺少 b，c 无法定位，只能用到 a |
| `b = 2` | ❌ 常规不行 | 无 | 缺少最左列 a |
| `b = 2 AND c = 3` | ❌ 常规不行 | 无 | 缺少最左列 a |
| `c = 3` | ❌ 常规不行 | 无 | 缺少最左列 a |
| `a > 1 AND b = 2 AND c = 3` | ⚠️ 部分 | 只有 a | a 是范围查询，后续列无法继续定位 |
| `a = 1 AND b > 2 AND c = 3` | ⚠️ 部分 | a, b | b 是范围查询，c 无法继续定位 |
| `a = 1 AND b = 2 AND c > 3` | ✅ | a, b, c | c 是范围查询，但已是最后一列，仍能用 |

**关键结论：**

1. **WHERE 条件书写顺序无所谓**，优化器会自动重排；
2. **查询条件必须包含最左列 `a`**，否则常规情况下用不上索引；
3. **范围查询会截断后续列**，`a > 1` 之后 `b`、`c` 无法继续定位；
4. **中间列缺失会导致后续列失效**，`a = 1 AND c = 3` 中 `c` 用不上。

#### 3.4.3 例外情况：索引跳跃扫描（Index Skip Scan）

MySQL **8.0.13+** 引入了 Index Skip Scan。当联合索引**最左列基数很低**（比如性别只有男/女两个值）时，即使 WHERE 不带最左列，优化器也可能用上索引：

```sql
-- 索引 idx_gender_age (gender, age)
-- gender 只有 'M' / 'F' 两个值
SELECT gender, age FROM user WHERE age = 25;

-- 优化器可能改写为类似：
-- (gender = 'M' AND age = 25) OR (gender = 'F' AND age = 25)
-- 相当于在索引上做多次范围查找

```

但这是**优化器的特殊能力**，不是最左前缀原则的常规表现，而且要求：

- MySQL 8.0.13+；
- 最左列基数很低（区分度很低）；
- 优化器认为收益大于全表扫描。
- Index Skip Scan 同样支持回表。它本质上是通过在索引前缀的各个不同值之间“跳跃”，把不带前缀的查询拆成了多个带前缀的子范围扫描（Range Scan），若查到主键仍需回表拿数据。
- 还受单表、无 GROUP BY/DISTINCT 等限制，且由优化器按代价决定是否使用。
- 这是优化器的特殊能力，不是最左前缀原则的常规表现。不要依赖 Index Skip Scan 来设计索引，正确做法还是按查询模式建联合索引。

#### 3.4.4 例外情况：覆盖索引全扫描

如果查询的列全部在索引里，即使不满足最左前缀，也可能走**全索引扫描**：

```sql
-- 索引 idx_abc (a, b, c)
SELECT a, b, c FROM t WHERE b = 2;
-- type = index，Extra = Using where; Using index
```

注意：

- `type = index` 表示**扫描整个索引**，不是 `range` 定位；
- 只是避免了回表，但扫描量可能很大；
- 效率通常不如 `range`，数据量大时仍可能很慢。

#### 3.4.5 联合索引设计建议

- **把等值查询列放前面，范围查询列放后面**；
- **把选择性高（基数大）的列放前面**，但也要考虑查询模式；
- **覆盖高频查询的列**，尽量让查询走覆盖索引；
- **避免冗余索引**，`(a, b)` 和 `(a, b, c)` 可以共存，但 `(a, b)` 和 `(a)` 通常只需要 `(a, b)`。

### 3.5 为什么 InnoDB 必须有主键？

因为 InnoDB 的数据组织方式就是聚簇索引，**数据必须挂在某个 B+ 树上**。没有主键时 InnoDB 会生成隐藏 `row_id`，但这样用户无法控制，不推荐。

## 四、总结

| 问题 | 答案 |
|---|---|
| **为什么用 B+ 树？** | 矮胖、扇出大、磁盘 IO 少；叶子链表支持高效范围查询和全表扫描；数据全在叶子层，查询性能稳定；天然有序，支持排序 |
| **聚簇索引是什么？** | 索引和数据在一起，叶子节点存整行数据；InnoDB 主键索引就是聚簇索引；一张表只有一个 |
| **非聚簇索引是什么？** | 索引和数据分离，叶子节点存索引列 + 主键值；查询非索引列需要回表；一张表可以有多个 |
| **核心区别** | 叶子节点存什么：整行 vs 主键；是否回表：不需要 vs 可能需要；数量：1 个 vs 多个 |
| **最左前缀原则** | WHERE 条件书写顺序无所谓，优化器会重排；真正约束是查询必须包含最左列，范围查询会截断后续列 |
| **优化要点** | 自增短主键、覆盖索引、联合索引最左前缀、避免 `SELECT *` 导致回表 |

**一句话记忆：**

> B+ 树是为磁盘 IO 和范围查询优化的多路平衡树；聚簇索引是"数据即索引"，非聚簇索引是"索引指向主键"，两者通过回表协作，覆盖索引是避免回表的关键手段。最左前缀原则约束的是"索引列顺序 + 是否包含最左列"，不是 WHERE 条件的书写顺序。

## 五、常见误区

1. **"WHERE 条件必须按索引列顺序写"**
   错。优化器会自动重排，`WHERE b=? AND a=?` 和 `WHERE a=? AND b=?` 对索引 `(a,b)` 等价。

2. **"bac、cba 不能用索引"**
   错。只要查询条件包含最左列 `a`，WHERE 条件写成什么顺序都能用。真正不能用的是缺少最左列，比如只写 `WHERE b=? AND c=?`。

3. **"联合索引 (a,b,c) 可以单独用 b 或 c"**
   需严格区分：单独用中间列 b 在 MySQL 8.0+ 有机会通过 Index Skip Scan 挽救（虽然会回表）；但如果只单独用最右列 c，则完全无法利用索引（Skip Scan 无法连续跳过两层），只能走全表扫描或全索引扫描。

4. **"范围查询后面的列还能继续用索引"**
   不能。`a > 1 AND b = 2` 中 `b` 无法继续定位，因为 `a` 是范围，`b` 在范围内不保证有序。

5. **"索引越多越好"**
   错。索引会增加写入成本、占用存储、可能让优化器选错索引。按查询模式建必要的索引即可。
